# TenantPulse

Internal **Microsoft 365** diagnostic and DNS-hygiene tool for MW N1
support. A **100% client-side** application: no backend, no dependencies, no data sent to a
server. All processing happens in the browser, which queries public APIs directly (Microsoft,
Google DNS, RDAP).

## Features

The app bundles three tools in a single interface:

| Tab | Folder | Purpose | Network |
|---|---|---|---|
| **M365 Diagnostic** | `/` (root) | Microsoft Tenant ID, Google Workspace detection, DNS (MX/SPF/DKIM/DMARC), WHOIS/RDAP, hosting provider | External public APIs |
| **Email headers** | `ML/` | Header analysis (SPF/DKIM/DMARC/EOP, SMTP chain, URLs), `.eml` import, client & technical reports | 100% local |

Two analysis depths for the M365 diagnostic:
- **Fast**: Tenant ID + basic DNS
- **Full**: adds DNS security (SPF/DKIM/DMARC scoring) and WHOIS/hosting provider

Optional Tenant ID history, stored only in the browser's `localStorage` (opt-in, configurable
auto-purge, never transmitted).

## Running locally

Serve the folder over HTTP — do not open `index.html` via `file://` (DoH/fetch requests and
cross-iframe theme sync require a real origin):

```bash
python3 -m http.server 8000
# then open http://localhost:8000
```

No build step: these are static files (HTML + CSS + JS + images).

## Architecture (summary)

- `index.html` + `tenantpulse.js` + `tenantpulse.css`: the shell (M365 Diagnostic).
- `ML/`: sub-app loaded as `<iframe ...?embedded=1>` inside the shell. Shares
  `tenantpulse.css` and communicates with the shell via `postMessage` (theme sync `tp-theme`,
  Diagnostic Messagerie profile `ml-profile`). Also works standalone.
- **Strict CSP** (`script-src 'self'`, no `unsafe-inline`): no inline scripts, no `onclick`
  handlers, no `innerHTML` from input — the DOM is built via `createElement`/`textContent`.

Full details in [`CLAUDE.md`](CLAUDE.md).

## Deployment — GitHub Pages

The site is published on **GitHub Pages** by `.github/workflows/github-pages.yml`, on every
push to `main` (or manually from the Actions tab). No build: the workflow copies the frontend
files (`*.html`, `*.js`, `*.css`, `assets/`, `ML/`) as-is; `api/`, `extension/` and the docs
are not published.

**One-time setup:** repository *Settings → Pages → Build and deployment → Source* =
**GitHub Actions**. The site is then served at `https://<owner>.github.io/<repo>/`.

What works without a backend: the whole M365 diagnostic (Tenant ID, Google Workspace, DNS,
SPF/DKIM/DMARC, WHOIS/RDAP, hosting provider), the email-header analyzer, local history,
profiles and settings — everything that runs in the browser.

What needs the Azure backend and is **hidden** on GitHub Pages: shared tenant tags and the
tenant directory, the information banner, the Microsoft Graph connection (its client ID is
served by `/api/me`), the browser extension (gated on a `/api/me` attestation) and the
**Logout** button. Detection is automatic (`TP_BACKEND` in `tenantpulse.js`: `/api/me`
answering 404 means a static host).

Without a backend the visitor is **admin of their own copy**: the *Administration* panel
shows the tabs that work from browser storage alone — today, the custom nav buttons
(*Bouton*), saved in `localStorage`. A default **Accès conditionnel** button (Entra
Conditional Access) is provided and can be edited or removed.

The page is **public**: GitHub Pages has no sign-in. The app processes no data server-side,
and its source is already public in this repository.

## Former deployment — Azure Static Web Apps

The app used to run on **Azure Static Web Apps** (dedicated subscription). The configuration is
kept for a possible return; its workflow (`azure-static-web-apps.yml`) is now manual-only.

- `staticwebapp.config.json` (at the root) delivers the **security HTTP headers** in
  production: real CSP (mirroring the `<meta>` + `frame-ancestors 'self'`), HSTS,
  `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, COOP.
- Resource group: `gr-tenantpulse-prod` (West Europe).
- Deployment ran from the `main` branch via GitHub Actions (workflow generated by Azure when
  the Static Web App resource was created). To go back, restore its `push` / `pull_request`
  triggers.

### Authentication & access (Azure only)

On Azure, the site is **fully private**, restricted to the organization via **Entra ID (Azure AD)** —
`staticwebapp.config.json` enforces `allowedRoles: ["authenticated"]` on all routes (`/*`). An
unauthenticated visitor (including on a `.js`/`.css` file) is automatically redirected to the
Microsoft sign-in (`responseOverrides` 401 → `/.auth/login/aad`).

- Provider: Azure Active Directory, dedicated tenant (`openIdIssuer`), `clientId`/`clientSecret`
  stored on the Azure side (`AAD_CLIENT_ID` / `AAD_CLIENT_SECRET` settings, never in the code).
- Routes: `/login` (sign-in), `/logout` (sign-out → `/.auth/logout`).
- A **Logout** button is available in the top bar (links to `/logout`).

Static Web Apps build settings:

| Setting | Value |
|---|---|
| App location | `/` |
| Api location | _(empty — no backend)_ |
| Output location | _(empty — no build)_ |
